## 1. RDS 생성 (참고 — 현재 미사용, RDS로 되돌릴 때만 읽는다)

### 1-1. 인스턴스
- 엔진 **MySQL 8.0.x**(최신 마이너), 클래스 **db.t4g.micro**(파일럿, 1 GiB) — 부족 신호는 CPU 크레딧 소진·`max_connections`(약 80) 도달. 축제 규모(부스 5~10, 동시 손님 수백)에는 micro로 충분하다고 **추정**한다(부하 시험은 하지 않았다)
- 스토리지 gp3 20 GiB, **퍼블릭 액세스 없음**, 보안 그룹은 EC2의 보안 그룹에서 3306만 허용
- **자동 백업 보존 7일**, 삭제 방지 켬. Multi-AZ는 파일럿에서 끔(비용)
- 마스터 계정은 스키마 적용에만 쓰고, 앱은 별도 계정 `boothlock_app`(해당 DB에 DML 권한만: SELECT/INSERT/UPDATE/DELETE. `validate`는 DDL 권한이 필요 없다)

### 1-2. 파라미터 그룹 (기본 그룹을 복제해 수정)
| 파라미터 | 값 | 이유 |
|---|---|---|
| `character_set_server` | `utf8mb4` | 이모지 등 4바이트 문자(메뉴명·피드백) — 스키마 SQL이 테이블마다 utf8mb4를 명시하므로 이중 방어 |
| `collation_server` | `utf8mb4_0900_ai_ci` | 8.0 기본. 토큰 3컬럼만 스키마에서 `utf8mb4_bin` |
| `time_zone` | `Asia/Seoul` | DATETIME은 타임존을 저장하지 않는다. JVM·JDBC·DB 셋을 KST로 (DB스키마 원칙 8). `NOW()`를 쓰는 수동 쿼리·백업 복원 시각 판독도 KST가 된다 |
| `transaction_isolation` | `READ-COMMITTED` | 앱 풀에서도 설정하지만(§3-4) DB 기본값도 맞춰 두면 수동 접속·다른 클라이언트도 같은 조건이 된다 |
| `binlog_format` | `ROW` (8.0 기본) | STATEMENT면 READ COMMITTED 트랜잭션이 거부된다. RDS 기본 그룹은 MIXED일 수 있는데 MIXED도 동작한다 |
| `max_connections` | 기본(메모리 비례) | 앱 풀 10 + 운영자 수동 접속 몇 개면 충분 |
| `innodb_lock_wait_timeout` | 기본 50 | 채번·입금확인 잠금은 ms 단위. 이 값이 문제되면 코드 결함이다 |
| `sql_mode` | 기본 (STRICT_TRANS_TABLES 포함) | 로컬 8.4 기본과 동일한 값으로 테스트했다. RDS 기본 그룹은 엔진 기본과 다를 수 있으니 생성 후 `SELECT @@sql_mode`로 확인 |

### 1-3. 로컬 검증(8.4.0)과 RDS(8.0)의 차이 — 확인 필요 항목
- **인증 플러그인**: 8.4는 `mysql_native_password`가 기본 비활성, `caching_sha2_password`만. RDS 8.0도 기본은 `caching_sha2_password`이며 Connector/J 9.x는 둘 다 지원한다. 앱 계정을 `IDENTIFIED WITH caching_sha2_password`로 만들면 양쪽 동일
- **sql_mode 기본값**: 8.0과 8.4의 엔진 기본값은 같다(`ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION`). RDS 파라미터 그룹이 이를 바꿔 두었을 수 있다
- **`lower_case_table_names`**: 로컬 macOS는 2, RDS(Linux)는 0. 테이블명이 전부 소문자라 영향 없음
- **기본 콜레이션**: 둘 다 `utf8mb4_0900_ai_ci`
- **TLS**: Connector/J 기본 `sslMode=PREFERRED`(암호화하되 CA 검증 없음). 같은 VPC 안이라 파일럿은 이대로 두고, 검증까지 하려면 URL에 `sslMode=VERIFY_CA&trustCertificateKeyStoreUrl=…`(RDS CA 번들) 추가

## 3. 스키마 (참고 — 현재 미사용, RDS로 되돌릴 때만 읽는다. H2는 `ddl-auto=update`로 자동 관리)

### 3-1. 왜 `validate`인가 (자동 변경 금지)
- Hibernate `update`는 **`COLLATE utf8mb4_bin`을 모른다.** 첫 배포를 `update`로 하면 `table_token`·`session_token`·`idempotency_key`가 대소문자 무시(ai_ci)로 만들어져 **틀린 토큰으로 인증이 통과**한다(실측). 엔티티 소스를 고치지 않는 한 SQL을 손으로 적용해야 하고, 그러면 그 뒤로는 `validate`가 맞다
- `validate`는 테이블·컬럼 존재와 JDBC 타입만 대조한다 — 콜레이션·추가 인덱스·FK는 통과하고, 엔티티에 컬럼이 추가된 채 SQL을 빠뜨리면 **기동 시 실패해 알려 준다**
- 절차: 엔티티를 바꾸면 `schema-mysql8.sql`에 `ALTER TABLE`을 같이 넣고 배포 전에 RDS에 먼저 적용한다

### 3-2. 적용
```bash
mysql -h <RDS> -u <admin> -p -e "CREATE DATABASE boothlock CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"
mysql -h <RDS> -u <admin> -p boothlock < backend/docs/schema-mysql8.sql
mysql -h <RDS> -u <admin> -p -e "CREATE USER 'boothlock_app'@'%' IDENTIFIED WITH caching_sha2_password BY '<pw>'; GRANT SELECT,INSERT,UPDATE,DELETE ON boothlock.* TO 'boothlock_app'@'%';"
# 확인
mysql -h <RDS> -u <admin> -p -e "SELECT table_name, column_name, collation_name FROM information_schema.columns WHERE table_schema='boothlock' AND collation_name='utf8mb4_bin';"
# → booth_table.table_token / table_session.session_token / orders.idempotency_key 세 줄
```

### 3-3. `DB스키마_v1.3.md` ↔ 실제 Hibernate DDL(MySQL) ↔ `schema-mysql8.sql` 차이

| 항목 | 문서 v1.3 | Hibernate가 만드는 것(실측, ddl-auto=create) | `schema-mysql8.sql` 채택 | 비고 |
|---|---|---|---|---|
| 시각 컬럼 | `DATETIME` | `datetime(6)` | **`DATETIME(6)`** | LocalDateTime 나노초. (0)으로 두면 반올림돼 `last_activity_at` 비교가 어긋날 수 있다 |
| BOOLEAN 컬럼 | `BOOLEAN` | `bit(1)` (columnDefinition 있는 `booth_table.active`·`order_item.canceled`만 `tinyint(1)`) | **`BOOLEAN`(=tinyint(1))** | Connector/J 기본 `tinyInt1isBit=true`라 validate가 BIT로 인식해 통과(실측) |
| `booth_table.status` | `VARCHAR(20)` | `varchar(20)` + CHECK (PR #54 최종 f5a4a21 기준. 통합본 초기에는 `@JdbcTypeCode` 누락으로 네이티브 `enum('EMPTY','OCCUPIED')`가 생성됐으며 port-fix2에서 수정) | **`VARCHAR(20)` + CHECK** | 엔티티와 일치 |
| `booth.depositor_name` | 미기재 | `varchar(50) DEFAULT NULL` (#57 예금주명) | **`VARCHAR(50) NULL` 추가** | 빠지면 validate가 `missing column [depositor_name]`으로 기동 실패 — f5a4a21 엔티티로 재대조해 추가(2026-09-16) |
| 열거형 CHECK | 없음 | `status`·`payment_status`·`payment_method`·`role`·`reason`에 CHECK 생성(Hibernate 7) | **채택(이름 부여)** | 최후 방어선 원칙(`DB스키마_v1.4.md` 설계 원칙 7)과 일치 |
| `table_token`·`session_token`·`idempotency_key` 콜레이션 | `utf8mb4_bin` | **없음(테이블 기본 ai_ci)** | **`utf8mb4_bin`** | 대소문자 무시면 틀린 토큰 인증 통과 — 이 파일을 손으로 적용해야 하는 이유 |
| `orders.session_id` 인덱스 | 없음 | `idx_orders_session` (f5a4a21 기준 엔티티 `@Index`에 있음 — 통합본 초기에는 없었음) | **`idx_orders_session`** | 세션별 주문·미결제 집계(C6·O6·좌석 현황)가 매번 orders 풀스캔이 되는 것을 막는다 |
| FK: `orders→booth`, `orders→table_session`, `feedback→booth/staff_account`, `daily_counter→booth` | 있음 | **없음**(엔티티가 `Long` 컬럼으로만 참조) | **추가** | 코드는 존재하는 id만 넣으므로 무해. 삭제 없음 원칙이라 ON DELETE 불필요 |
| FK/UK 이름 | `fk_*`, `uq_*` | `FKokcuhbk…`, `UKen3mtb2…` 해시 | 문서 이름 | validate는 이름을 보지 않는다 |
| `daily_counter` PK 컬럼 순서 | `(booth_id, business_date)` | `(business_date, booth_id)` | 문서 순서 | 조회가 항상 두 컬럼을 다 쓰므로 어느 쪽이든 인덱스 활용은 같다 |
| `booth.next_table_seq` | 미기재 | `int NOT NULL DEFAULT 1` | 추가 | 테이블 자동 채번(O2) — 문서 v1.3 이후 추가된 컬럼 |
| `booth_table.active` | 미기재 | `tinyint(1) NOT NULL DEFAULT 1` | 추가 | soft delete |
| `menu.category`, `uk_menu_booth_name` | 미기재 | 있음 | 추가 | 메뉴 분류·부스 내 메뉴명 유일 |
| `order_item.canceled` | 미기재 | `tinyint(1) NOT NULL DEFAULT 0` | 추가 | 항목 개별 취소 |
| `staff_account.failed_login_count` 등 DEFAULT | 문서에 DEFAULT | Hibernate는 DEFAULT를 안 만든다(엔티티 초기값으로 INSERT) | 문서 DEFAULT 유지 | 수동 INSERT 편의 |
| `booth_table.status` DEFAULT 'EMPTY' | 있음 | 없음 | 유지 | 〃 |

→ **문서 v1.3 개정 제안**: DATETIME(6), 위 미기재 컬럼 6개(`depositor_name` 포함), 열거형 CHECK, `idx_orders_session`을 반영.

**전수 대조 결과(f5a4a21 엔티티 ↔ 이 SQL, 2026-09-16)**: Hibernate `create`로 만든 DB와 이 SQL을 적용한 DB의 `information_schema`를 비교 — 컬럼 99개 전부 이름·타입·길이·NULL 일치(bit(1)↔tinyint(1)만 동치로 봄), 인덱스 차이는 의도한 2건(`daily_counter` PK 컬럼 순서, 위 FK 추가에 따른 `feedback` FK 인덱스)뿐, CHECK 제약 6=6. 이 SQL을 적용한 DB에 PR #54 최종 코드를 prod 프로필(`validate`)로 기동해 통과.

### 3-4. 격리수준 — MySQL에서만 드러난 동시성 결함과 대응
전체 테스트를 MySQL 8.4에서 두 번 돌렸다(각 629건).

| 조건 | 결과 | 실패 목록 |
|---|---|---|
| InnoDB 기본 **REPEATABLE READ** | **624 통과 / 5 실패**(하네스 문제 제외) | `OrderEditConcurrencyTests` 3건(`cancelingTwoItemsConcurrently…`, `lastItemCancelRacingPayment…`, `customerCancelRacingPayment…`), `TableCheckoutConcurrencyTests.checkoutWaitsForInFlightOrder…`, `TableSoftDeleteGuardTests.deleteRacingFirstScan…` |
| 풀 격리수준 **READ COMMITTED** (`spring.datasource.hikari.transaction-isolation`) | **628 통과 / 1 실패**(하네스 문제) | 동시성 테스트 전부 통과. 판정 순서 양쪽 모두 관측됨(예: 두 항목 취소 23/17, 취소 vs 입금 20/20, 삭제 vs 스캔 99/1) |

원인은 다섯 건이 같다: 서비스가 **인증용 일반 SELECT(스냅샷 고정) → `SELECT … FOR UPDATE` 잠금 대기 → 풀린 뒤 관련 행을 다시 읽어 판정**하는 구조인데, REPEATABLE READ에서는 그 재읽기가 잠금 이전의 옛 스냅샷을 본다(H2 기본 READ COMMITTED에서는 매 문장마다 새 스냅샷). 가장 위험한 것은 `DashboardOrderActionService.cancelItem`: 두 운영자가 서로 다른 항목을 동시에 취소하면 상대 항목의 취소를 보지 못해 **모든 항목이 취소됐는데 주문은 RECEIVED·합계는 옛값**으로 남는다. 나머지는 409 사유 코드 오류(`ALREADY_PAID`↔`INVALID_STATE`), 퇴실 미결제 경고 누락, 삭제 직전 스캔 세션이 붙은 채 테이블 비활성화.

대응(둘 다 적용): ① 운영 프로필 풀 격리수준 READ COMMITTED(실측으로 해소 확인) ② RDS 파라미터 `transaction_isolation=READ-COMMITTED`. **권장 코드 수정**(설정 의존을 없애기): 해당 `@Transactional`에 `isolation = Isolation.READ_COMMITTED`를 명시하거나, 잠금 획득 뒤 `entityManager.refresh(order)`로 항목을 다시 읽는다.

남은 1건 `EventSeederStartupTests.failureDuringApplyRollsBackEverything`은 검증용 임시 프로필의 `ddl-auto=create`가 "첫 기동으로 만든 스키마에 충돌 행을 넣고 두 번째 기동이 실패하길 기대"하는 시나리오의 충돌 행을 지운 탓이다(H2 파일 DB로 도는 테스트라 MySQL과 무관). 잠금 대기 초과·데드락·갭 락 오류는 두 실행 모두 **0건**.

## 4. 첫 배포 순서 (EC2)

0. EC2(Ubuntu 22.04+, t3.small 권장 — JVM 힙 + 도커) 에 docker·docker compose 설치, 보안 그룹 **22(내 IP만)·80·443** 공개(8080은 열지 않는다 — API는 프론트 컨테이너가 내부망으로만 접근). 80은 닫으면 안 된다: 443으로 넘기는 리다이렉트와 인증서 갱신(certbot)이 그 포트를 쓴다. 저장소 clone
1. **환경변수** — `cp .env.prod.example .env.prod` 후 값 채우기(§2). `chmod 600 .env.prod`. `BOOTLOCK_CUSTOMER_BASE_URL`·`BOOTLOCK_CORS_ALLOWED_ORIGINS` 둘 다 EC2 퍼블릭 IP(또는 퍼블릭 DNS) 기준 `http://<EC2>` 하나로 맞춘다(포트 80은 http 기본이라 생략) — 프론트·API가 같은 오리진으로 나가므로 이 값들은 사실상 QR·기동 필수값 통과용이고 실제 CORS 차단은 일어나지 않는다
2. **DB·업로드 폴더·시딩 파일**
   ```bash
   mkdir -p data/db data/uploads/menu data/uploads/event seed
   cp <약도.png> data/uploads/event/            # 시딩 파일 eventMap.imageUrl 이 가리키는 이름으로
   cp <event-seed.json> seed/event-seed.json    # 형식: backend/src/main/resources/seed/event-seed.example.json
   sudo chown -R 10001:10001 data                # 컨테이너 비루트 사용자(uid 10001)가 써야 한다 (data/db 포함)
   ```
3. **시딩 켜서 1회 기동** — `.env.prod`에 `BOOTLOCK_SEED_ENABLED=true`, 비밀번호 변수들 채운 뒤
   ```bash
   docker compose -f docker-compose.prod.yml up -d --build   # api + frontend 둘 다 빌드·기동
   docker compose -f docker-compose.prod.yml logs -f api     # "Started BoothlockServerApplication" 과 시딩 로그 확인
   curl -s localhost:8080/api/v1/event/booths                # 부스 목록이 보이면 시딩 완료
   curl -s -o /dev/null -w "%{http_code}\n" localhost:8080/api/v1/event/map   # 200
   curl -s -o /dev/null -w "%{http_code}\n" localhost/         # 200 이면 프론트도 정상
   curl -s -o /dev/null -w "%{http_code}\n" localhost/api/v1/event/booths   # 200 이면 nginx→api 내부 프록시까지 정상
   ```
   시딩 파일이 틀리면 기동이 실패하고 원인이 로그에 있다(약도 파일 없음·loginId 중복 등). 두 번 켜도 중복 삽입은 없다. H2는 `ddl-auto=update`라 스키마를 미리 적용할 필요가 없다 — 첫 기동에서 테이블이 자동으로 생긴다
4. **시딩 끔** — `BOOTLOCK_SEED_ENABLED=false`로 바꾸고 `docker compose -f docker-compose.prod.yml up -d` (재생성). 시딩 비밀번호 변수는 지운다
5. **운영자 첫 로그인** (`http://<EC2>/`) → 부스별 ADMIN이 비밀번호 변경, 테이블 등록(O2), QR PDF 다운로드(O4b) → 인쇄. **QR에 박히는 주소 = `BOOTLOCK_CUSTOMER_BASE_URL`** 이므로 이 값을 바꾸기 전에 인쇄하지 않는다. 계좌번호 "복사" 버튼(`navigator.clipboard`)은 HTTPS에서만 동작하는데, 지금은 HTTPS라 정상이다 (HTTP로 띄우던 시기에는 브라우저가 조용히 막았다)

### 재배포(코드 변경)

EC2에 SSH로 들어가서 한다. 아이디·비밀번호가 아니라 **키 파일(.pem)** 방식이고, Ubuntu AMI의 계정명은 `ubuntu`다.
키는 인스턴스를 만들 때 한 번 발급되며 **콘솔에서 새로 만들어도 이미 떠 있는 인스턴스에는 적용되지 않는다** —
키가 없으면 인스턴스를 세운 사람에게 받아야 한다.

```bash
ssh -i <키파일.pem> ubuntu@<EC2 퍼블릭 IP 또는 DNS>   # 키 파일은 chmod 400 이어야 붙는다
cd <저장소 경로>
git pull && docker compose -f docker-compose.prod.yml up -d --build   # graceful shutdown 8초 — 처리 중 요청을 끝내고 교체
```

**배포됐는지 확인** — 서버 밖에서 바로 볼 수 있다. 엔드포인트 존재 여부로 버전을 가늠한다.
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://booothlook.com/api/v1/admin/orders/1/restore -X POST
#   401 = 최신(#71 이후) / 404 = 그 이전 코드
curl -s -o /dev/null -w "%{http_code}\n" https://booothlook.com/api/v1/admin/reports/settlement.csv
#   401 = 최신(#84 이후) / 501 = 아직 스텁이던 그 이전 코드
```
H2 `ddl-auto=update`라 엔티티에 컬럼이 늘어도 자동으로 반영된다(컬럼 **삭제·타입 변경**은 update가 못 미더우니 파일럿 기간엔 하지 않는다). `./data/db` 볼륨은 재배포해도 그대로 남는다. 프론트는 소스가 안 바뀌었으면 재빌드해도 도커 레이어 캐시로 빨리 끝난다.

## 5. 프론트 배포 — 같은 EC2에 컨테이너로, API는 내부망으로만 (팀 결정)

`docker-compose.prod.yml`의 `frontend` 서비스가 `frontend/Dockerfile`로 Vite 빌드 → nginx 정적 서빙까지 한 번에 한다. §4에서 `up -d --build`를 돌리면 API와 같이 빌드·기동된다 — 별도 배포 단계 없음.

- **API 주소를 빌드에 안 박는다**: `VITE_API_BASE_URL`을 비워 둬서 프론트는 상대경로(`/api/...`, `/uploads/...`)로만 호출한다. 이 요청은 nginx(`frontend/nginx.conf`)가 받아 도커 내부망(서비스명 `api`)으로 api 컨테이너에 중계한다 — 그래서 브라우저 기준 프론트·API가 **같은 오리진**이 되어 CORS가 필요 없고, EC2 주소(IP)가 바뀌어도 프론트를 다시 빌드할 필요가 없다(내부 중계 주소 `http://api:8080`은 안 바뀌므로)
- **SPA 라우팅**: 같은 `nginx.conf`가 `/api`·`/uploads` 이외의 경로는 `try_files $uri $uri/ /index.html;`로 처리 — `/t/{tableToken}` 같은 경로를 새로고침해도 200으로 index.html을 준다
- **업로드 용량**: `nginx.conf`에 `client_max_body_size 6m` — 메뉴 사진 5MB 상한보다 커야 한다(nginx 기본 1MB로 두면 사진 업로드가 API까지 가기 전에 413으로 막힌다)
- API 컨테이너는 `127.0.0.1:8080`으로만 열려 있다 — EC2 안에서 curl로 진단할 때만 쓰고, 외부에서 직접 붙을 수 없다(보안 그룹에 8080을 열 필요 자체가 없음)
- `BOOTLOCK_CUSTOMER_BASE_URL`·`BOOTLOCK_CORS_ALLOWED_ORIGINS` = 손님이 QR로 들어올 주소(`http://<EC2>`) — EC2 주소가 바뀌면(재배포로 새 인스턴스 등) 이 두 값만 바꾸면 된다(프론트 재빌드는 필요 없음)
- 이미지(`/uploads/menu/…`, `/uploads/event/…`)도 같은 오리진의 상대경로라 `frontend/src/lib/apiBase.ts`가 별도 베이스 없이 그대로 쓴다
- **나중에 규모가 커지면**: S3+CloudFront나 Vercel로 프론트만 분리하고 도메인·HTTPS를 붙이는 것도 고려할 수 있다 — 그때는 프론트 빌드에 `VITE_API_BASE_URL=https://api.<도메인>`을 다시 넣어 API를 직접 호출하게 하고, `docker-compose.prod.yml`에서 `frontend` 서비스를 빼고 `api`의 8080을 필요한 만큼 공개하면 된다

### 운영 중 볼 것
- 로그: `Lock wait timeout`, `Deadlock`(즉시 보고 — 테스트에서는 0건), `HHH` Hibernate 오류

## 7. "SQS 등 분리 아키텍처"에 대해 (멘토 요구사항)

**지금 넣지 않는 근거**
- 이 시스템에서 비동기로 떼어낼 수 있는 일은 하나뿐이다 — **계좌 변경 웹훅 알림**(`BoothWebhookNotifier`, O17). 그것도 이미 `HttpClient.sendAsync`로 요청 스레드를 막지 않으며 실패는 로그로만 남긴다(주문 흐름과 무관)
- 주문 접수·채번·입금확인·퇴실은 **동기 트랜잭션이 곧 정확성**이다: 채번은 `SELECT … FOR UPDATE`로 순번을 잠그고, 세션 유일성은 UNIQUE 제약이 강제하며, 손님은 응답으로 주문번호·계좌 안내를 즉시 받아야 한다. 큐를 끼우면 "주문이 접수됐는지"를 손님이 폴링해야 하고, 실패 재시도·멱등 처리·순서 보장을 새로 만들어야 한다 — 파일럿 규모(부스 5~10, 초당 주문 수 건)에서 얻는 것이 없다
- 앱 서버 1대·DB 1대 구성에서 큐 컴포넌트를 더하면 장애 지점과 운영 부담(IAM·DLQ·모니터링)만 늘어난다. 축제 당일 팀이 볼 수 있는 대상은 컨테이너 로그와 RDS 콘솔 두 개가 한계다

**파일럿에서 넣을 수 있는 자리(다음 단계 후보)**
1. **알림 아웃박스 → SQS → 소비자**: 계좌 변경·주문 접수 시 `notification_outbox` 테이블에 행을 트랜잭션 안에서 넣고, 별도 워커가 SQS로 보내 Slack/카카오 알림톡 등으로 전달. 웹훅 유실(현재는 로그만)을 없애고, 알림 채널을 API 서버에서 분리한다. 코드 변경 범위가 작고(O17 한 곳 + 아웃박스 폴러) 실패해도 주문에는 영향이 없어 **첫 분리 대상으로 적합**
2. **정산 CSV(O19) 생성**: 행사 후 일괄 작업이라 큐에 넣고 S3에 파일을 떨어뜨린 뒤 링크를 주는 형태가 자연스럽다 — 다만 지금 데이터 양(부스당 수백 건)에서는 동기 응답 1초 미만이라 필요성이 없다
3. **좌석 현황(E1) 집계 캐시의 갱신**: 폴링 API가 10초 캐시로 DB를 보호하고 있는데, 세션 변경 이벤트를 큐로 흘려 캐시를 갱신하면 지연을 없앨 수 있다 — 프론트 폴링 주기(12초)와 비슷해 파일럿에서는 체감 이익이 없다

정리: 멘토에게는 "분리 가능 지점을 식별했고(1번), 파일럿은 단일 트랜잭션 정확성과 운영 단순성을 택했다. 다음 행사에서 알림 아웃박스+SQS를 첫 분리로 넣는다"로 답한다.
