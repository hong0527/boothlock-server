## v0.5에서 확정이 필요한 항목 (팀 확인 후 이 절을 지운다)

| # | 항목 | 이 명세서가 택한 값 | 확정이 필요한 이유 |
|---|---|---|---|
| 1 | **파일럿 부스 수** | **복수** | 홈 화면 지도의 전제다. 부스가 하나면 핀이 하나뿐이라 화면의 실익이 없다. **다만 비용이 있다** — ① O10·O15·C6의 임시 파라미터가 실제 취약점이 된다(§7-21) ② 부스·계정·약도 시딩이 신규 작업으로 생긴다 ③ 부스마다 계정·테이블·QR 인쇄가 배수로 는다. **대안**: 단일 부스를 유지하고 결정 3(운영자 POS)만 실행하는 것도 가능하다 |
| 2 | **좌석 현황 표시 방식** | 서버는 **숫자**(total·empty), 화면은 **3단계 변환** | 기능명세 1.8은 "여유/보통/만석 3단계, 정확한 좌석 수 미표기"다. 서버가 숫자를 주면 임계값을 프론트 배포만으로 조정할 수 있다. "숫자를 아예 내려주지 말자"는 판단도 가능하다 |
| 3 | **부스 약도 좌표 입력 주체** | 총관리자 시딩으로 초기값 + 운영자가 O17로 조정 | 운영자에게 열면 부스끼리 핀이 겹칠 수 있다. 주최측 일괄 배치로 잠그는 선택지도 있다 |
| 4 | **홈 화면 백엔드 담당** | **홍화수 (신규 `event/` 파트)** | 기존 6개 파트 어디에도 속하지 않는다. **주의**: 신규 패키지라도 이 개정은 아래 5번처럼 4개 파트 파일에 걸친다 |
| 5 | **개정 작업의 파트별 분담** | 아래 표 | 한 사람이 다 할 수 없다. CONTRIBUTING 0-3(남의 파트 파일 수정 금지) 절차를 각 항목에 적용해야 한다 |
| 6 | **O3 응답 형태** | **합집합 제안** — 기존 `needsCleanup` 유지 + `session`·`unpaidOrderCount`·`posX`·`posY` 추가 (O3 각주) | 명세는 `session`·`unpaidOrderCount`, 구현(#32 머지분)은 `needsCleanup`이다. 필드를 빼지 않고 더하기만 하면 쓰고 있는 화면이 깨지지 않는다. 한쪽으로 줄일지는 회의에서 정하고, O22 응답도 여기 따른다 |
| 7 | **`category` 값 체계** | `FOOD` / `CAFE` / `GOODS` / `ETC` | 회의는 컬럼 추가만 정했고 값은 정하지 않았다. 축제 부스 종류에 맞는지 확인 필요 |
| 8 | **시딩 산출물 형식·담당** | 미정 (`data.sql` 또는 시더 클래스) | §5 시딩 절 참조. 복수 부스로 가면 실질 필수 작업이다 |
| 9 | **좌석 유휴 임계 (v0.5.1 신설)** | **3시간** (`boothlock.event.seat-idle-minutes`) | E1이 "손님이 떠났다"고 판정하는 기준이다. 짧으면 아직 있는 손님 자리가 빈자리로 보이고, 길면 떠난 자리가 계속 만석으로 잡힌다. 축제 주점 평균 체류 시간을 아는 사람이 값을 정하는 게 맞다. 설정값이라 행사 당일에도 재배포 없이 바꾼다 |

# 1. 공통 규약

## 1.1 기본

| 항목 | 규칙 |
|---|---|
| 프로토콜 | HTTPS 필수 (HTTP 접근 시 리다이렉트 + HSTS 헤더) |
| 형식 | REST + JSON (UTF-8), `Content-Type: application/json` |
| 경로 | **공개 `/api/v1/event/...`** / 소비자 `/api/v1/...` / 부스 운영자 `/api/v1/admin/...` / 총관리자 `/api/v1/super/...` |
| 날짜·시각 | ISO 8601, 오프셋 포함 (예: `2026-09-15T18:30:00+09:00`) |
| **영업일** | **06:00 ~ 익일 05:59 (Asia/Seoul)** — "오늘/당일"이 붙는 모든 것(O10 대시보드·O18 매출·O19 정산·주문번호 채번·세션 만료)은 이 기준. **계산식: `businessDate = (해당 시각 − 6시간)의 날짜`** — 예: `2026-09-16T01:30+09:00` 주문 → businessDate = `2026-09-15`. `createdAt`의 캘린더 날짜를 그대로 쓰면 자정에 주문번호가 리셋되고 매출이 쪼개지므로 금지 |
| 금액 | 정수(원 단위). 소수점 없음 |
| ID | 서버 발급 정수 (`orderId`, `menuId`, `tableId` …) |
| 페이지네이션 | 파일럿 범위에서는 없음 (부스 수십 개·행사 2~3일 규모 — 전체 반환). v0.5에서 복수 부스로 전환했으나 목록 크기가 페이지네이션을 요구할 규모는 아니다 |
| **부스 수** | **복수** (v0.5 변경 — 홈 화면 지도의 전제). 부스 등록·계정 발급은 총관리자가 시딩으로 처리(§5). 각 부스의 데이터는 JWT `boothId`로 격리한다 — **단 이 격리는 현재 코드에 없다**. O10·O15·C6가 아직 임시 쿼리 파라미터(`boothId`·`sessionId`)를 그대로 신뢰하므로, **복수 부스로 가기 전에 이 셋의 JWT·세션 인증 전환이 선행되어야 한다** (§7-21) |

## 1.2 인증 — 4계층 (v0.5: 공개 축 신설)

| 대상 | 롤 | 방식 | 전달 | 발급 |
|---|---|---|---|---|
| **누구나 (홈 화면)** | — | **없음 (공개)** | — | — |
| 소비자 | — | 테이블 **세션 토큰** | 헤더 `X-Session-Token: {token}` | `POST /api/v1/table-sessions` (QR 토큰 검증) |
| 부스 운영자 | `STAFF` / `ADMIN`(부스 대표) | **JWT** | `Authorization: Bearer {token}` | `POST /api/v1/admin/auth/login` |
| 총관리자 (부스락 운영팀) | `SUPER_ADMIN` | **JWT** | 〃 | 〃 (계정은 시딩) |

**롤 규칙 (검증 반영 — 경계를 문장이 아니라 경로로 긋는다)**
- `STAFF`: 자기 부스의 일반 운영 전부 — 주문·메뉴·테이블·호출·퇴실·취소(O13)·환불확인 제외 전부. **부스 설정(O17)의 name·operatingHours·isOpen도 STAFF 변경 가능** (재료 소진 시 STAFF가 즉시 주문 마감할 수 있어야 함)
- `ADMIN`: STAFF 권한 + O17 요청 본문의 **`bankAccount` 필드** 변경 + 환불 완료 처리(O21). 엔드포인트 단위가 아니라 **필드/기능 단위** 상위 권한
- `SUPER_ADMIN`: `/api/v1/super/*` **전용**. `boothId = null`(무소속)이므로 **`/api/v1/admin/*` 호출 시 `403 FORBIDDEN`** (스코프를 특정할 수 없음 — "스코프 검사 예외" 같은 개념은 없음). 부스 데이터 열람이 필요해지면 8.5 중앙 관리자(Later)에서 별도 설계
- 부스 운영자(`STAFF`/`ADMIN`)가 `/api/v1/super/*` 호출 시 `403 FORBIDDEN`
- 권한 필터는 경로 프리픽스 세 줄로 끝남: `/event/* → 인증 없음`, `/admin/* → boothId 있는 JWT만`, `/super/* → SUPER_ADMIN만`

**공개 축(`/api/v1/event/*`) 규칙 (v0.5 신설 — 인증이 없으므로 노출 범위를 명세로 못박는다)**
- 목적: **대표 QR(축제장 입구·포스터)** 로 들어오는 홈 화면. 축제장에서 부스 위치를 찾고 자리 여유를 보는 용도. 대표 QR은 토큰이 없는 단순 링크라 이 축에는 식별자가 오가지 않는다
- **노출 가능**: **부스 식별자(boothId)**·부스명·카테고리·주문 접수 여부(isOpen)·전체 테이블 수·빈 테이블 수·약도 좌표·약도 이미지 주소·**약도 원본 크기(width·height)**·**약도 갱신 시각**
- **노출 금지**: 계좌(`bankAccount`)·매출·주문 내역·메뉴 가격·운영자 정보·`tableToken`·`sessionToken`. 인증이 없으므로 이 목록에 없는 필드는 추가하지 않는다
- 쓰기 없음 — GET만. 상태를 바꾸는 공개 엔드포인트는 만들지 않는다
- 폴링 대상이므로 **서버 캐시 10초** 권장. 부스 수십 개 × 관람객 수백 명이 동시에 새로고침해도 DB 부하가 선형으로 늘지 않게 한다
- 개인정보 없음 — 이 축은 손님을 식별하지 않는다 (세션·쿠키 미사용)

**토큰 2종 구분 (혼동 주의)**

| 토큰 | 위치 | 수명 | 역할 |
|---|---|---|---|
| `tableToken` | QR 인쇄물 (URL 형태: `https://{도메인}/t/{tableToken}`) | 재발급 전까지 유지 | "이 QR이 어느 테이블인가" 식별. 추측 불가 무작위값(CSPRNG 128bit+) — 테이블 번호·순번 기반 금지 (기능 0.1 "비밀 링크"). **클라이언트는 세션 교환 후 보관하지 않음** (§7-8) |
| `sessionToken` | 세션 발급 응답 → 브라우저 저장 (**쿠키 금지, 커스텀 헤더 유지** — CSRF 원천 차단) | 아래 3가지 중 먼저 오는 시점에 무효화: ① 퇴실 처리(O6) ② 유휴 만료 ③ 영업일 종료(06:00) | "이 테이블의 이번 이용" 식별. 주문·호출 API 인증 |

**세션 유휴 만료 규칙 (검증 반영 — 정상 손님을 끊지 않도록 정밀화)**
- "활동"의 정의: 주문(C3)·호출(C6)·**조회 폴링(C4)** 전부 포함 — 화면을 켜두고 있으면 이용 중으로 간주
- 마지막 활동 후 **3시간** 경과 시 자동 종료. 단 **미결제(RECEIVED+UNPAID) 주문이 남은 세션은 유휴 만료 제외** — 영업일 종료(06:00)로만 만료 (미결제 주문이 손님 화면에서 사라져 중복 주문을 유발하는 사고 방지)
- 자동 만료는 **세션만** 종료 — 테이블 status는 건드리지 않음 ("빈자리 전환은 수동만" 결정 유지). 목적은 퇴실 버튼 누락 시 세션이 무기한 사는 것 방지

- **세션은 테이블 단위**: QR 재스캔 시 활성 세션이 있으면 기기와 무관하게 그 세션 반환 → 주문 내역 자동 복원 (기능 0.2 충족, 별도 API·전화번호 불필요)
- 만료된 sessionToken으로 호출 시 `410 SESSION_EXPIRED` → "QR을 다시 스캔해주세요" 안내 (재스캔하면 C1이 새 세션 발급)
- JWT 클레임: `staffId`, `boothId`, `role`, **`pwdAt`(비밀번호 변경 시각)**. 만료 12시간. 매 요청 시 ① `StaffAccount.active` 확인 (정지 즉시 반영) ② `pwdAt < StaffAccount.passwordChangedAt`이면 `401` — **비번 재발급 시 기존 JWT 즉시 무효** (계정 탈취 의심 시나리오 대응, 검증 반영)
- 모든 `/admin/*` API는 JWT의 boothId 소속 데이터만 접근 (기능 8.1)

## 1.3 공통 에러 포맷

```json
{
  "error": {
    "code": "SOLD_OUT",
    "message": "품절된 메뉴가 포함되어 있습니다.",
    "details": [ { "menuId": 3, "menuName": "김치전" } ]
  }
}
```

- `code`: 클라이언트 분기용. `message`: 그대로 사용자에게 보여도 되는 한국어 문장. `details`: 선택 (에러별 상이)

| 500 | `INTERNAL_ERROR` | 서버 오류 — 발생 시 디스코드/슬랙 웹훅 자동 통보 (기능 9.2) |
| 501 | `NOT_IMPLEMENTED` | (개발 중 임시) 아직 구현되지 않은 스텁 API 호출 — 전 파트 구현 완료 시 자연 소멸 |

# 2. 주문·결제 상태 모델 (확정 — 기능 5.2)

```
[소비자 주문 생성] ──► RECEIVED (접수됨, 자동)
                        ├─ 운영자 [완료] ──► DONE (종결)
                        └─ 취소 ──► CANCELED (사유·취소자 기록, 종결)

결제 상태 (별도 축):
  UNPAID ──(운영자 입금확인 O11)──► PAID
  PAID 주문 취소 시 ──► REFUND_NEEDED ──(운영자 환불완료 O21)──► REFUNDED
```

| 규칙 | 내용 | 근거 |
|---|---|---|
| 소비자 취소 | `RECEIVED` **그리고** `UNPAID`일 때만 | 2.5 "접수대기 상태만 직접 취소" + 팀 결정(입금 후 취소는 운영자 경로 5.5로 일원화). CSV 2.5의 "조리 시작 후엔 운영자 요청"은 §7-1 운영 규칙("입금 확인 후 조리") 덕분에 **PAID = 조리 시작의 프록시**가 되어 충족됨 — 조리 상태 축이 없어도 논리가 닫힘 |
| 운영자 취소 | RECEIVED·DONE 어느 단계에서든 가능(실수 보정 포함), 취소 사유 필수 + **취소자·시각 자동 기록**. `PAID`였다면 자동 `REFUND_NEEDED` | 5.5 "어느 단계에서든" |
| 오취소 복구 | 취소는 종결 상태 — 복구 경로 없음. 잘못 취소했으면 **O14 수기 주문으로 재입력** (새 주문번호 발급). 실제 송금 없이 O21을 눌러 지우는 것 금지 (허위 환불 기록) | 검증 반영 |
| 환불 | **전액 취소만**. 환불 송금은 시스템 밖(운영자 직접 이체) — 송금 후 O21로 `REFUNDED` 처리. 미처리 목록 = O10에서 `paymentStatus=REFUND_NEEDED` 필터 (전일 건은 `businessDate` 파라미터로 조회) | 5.5 + 검증 반영 |
| 매출 집계 | `paymentStatus = PAID` 기준. REFUND_NEEDED/REFUNDED는 매출 제외 + O18에서 별도 집계 | 7.1 |
| 선결제 여부 | "입금 확인 후 조리"는 운영 규칙 — 서버 강제 없음, 대시보드 미결제 뱃지 표시. **단 위장 주문 방어선이므로 행사 중 필수 준수** (§7-1) | 5.2 |

**주문번호(orderNo) 채번 — 검증 반영으로 v0.4.1에서 변경, v0.4.2에서 구현 방식 확정 (중요)**

- 규칙: `{정규화된 테이블라벨}-{부스 영업일 통산번호}` — 예: `A3-17` = A-3 테이블에서 발생한, 이 부스의 이 영업일 17번째 주문
- 정규화: 라벨에서 하이픈·공백 제거 (`A-3` → `A3`) — 입금자명 "김철수A3-17"이 깔끔해지고 검색 파싱 단순
- 카운터는 **부스 단위, 영업일마다 1부터 리셋**. ~~세션 단위 회차~~는 테이블 회전 시 중복 발급으로 입금 대조(5.4 Must)가 깨져 폐기. ~~DB auto-increment~~도 영업일 리셋이 안 되므로 사용 불가 (2일차 첫 주문이 A3-89가 되는 결함 — 검증 반영)
- **채번 구현**: `SELECT COALESCE(MAX(orderSeq),0)+1 FROM orders WHERE boothId=? AND businessDate=? FOR UPDATE` (또는 별도 `booth_daily_counter` 테이블에 `SELECT ... FOR UPDATE` 후 +1). `unique(boothId, businessDate, orderSeq)` 제약은 최후 방어선 — 제약 위반 예외 시 최대 3회 재시도, 그래도 실패하면 500
- `businessDate`는 §1.1 계산식 (`시각 − 6시간`의 날짜)
- **orderNo는 영업일 안에서만 유일** — 2일차에 `A3-17`이 다시 나옴. 검색·대조는 항상 영업일 범위 내에서 수행 (O10 참조)
- 수기 주문(테이블 미지정)은 같은 시퀀스로 `M-{통산번호}` — 별도 카운터 없음
- CSV 요구 "같은 테이블이 여러 번 주문해도 구분됨"(2.3) 충족: 같은 영업일 안에서 통산번호는 항상 다름

> **손님 여정 (v0.5 정정)**: **축제장 입구·포스터의 대표 QR을 찍어 홈 화면(약도)으로 들어오고 → 지도에서 부스 위치를 보고 필요하면 부스별 자리 현황을 확인한 뒤 → 그 부스에 가서 테이블 QR을 찍고(C1) → 메뉴판(C2) → 주문(C3) → 상태 확인(C4)**
>
> **QR은 두 종류다.**
>
> | QR | 붙는 곳 | 찍으면 | 서버 |
> |---|---|---|---|
> | **대표 QR** | 축제장 입구·포스터 등 공용 위치 | 홈 화면(약도) 주소가 열린다 | **서버 작업 없음** — 홈 화면 URL을 가리키는 단순 링크다. 토큰·식별자가 들어가지 않으므로 발급·검증 API가 필요 없다 |
> | **테이블 QR** | 각 테이블 | 그 테이블의 세션이 시작된다(C1) | `tableToken` 검증 필요 (§1.2) |
>
> 대표 QR은 누구나 찍는 공용 물건이라 **개인을 식별하지 않는다.** 그래서 홈 화면이 공개 축(`/api/v1/event/*`)인 것이고, 인증이 시작되는 지점은 여전히 테이블 QR이다.

## 홈 화면 구성 (v0.5 확정 — E1·E2가 함께 쓰이는 방식)

대표 QR을 찍으면 열리는 화면이다. **지도가 메인이고, 자리 현황은 그 위에 얹히는 부가 기능이다.**

- **주(主): 약도 위 부스 위치** — 손님이 "어디로 가야 하지"를 푸는 것이 이 화면의 첫 번째 목적이다. 약도에는 부스 핀만 깔끔하게 찍고 정보를 많이 얹지 않는다 (E2 + `booth.mapX·mapY`)
- **부(副): 부스별 자리 현황 보기** — 지도 위쪽에 두어 필요할 때 확인한다. 부스마다 몇 테이블이 차 있는지를 목록으로 본다 (E1)
- 두 API는 **각각 독립적으로 호출**한다. 약도(E2)는 진입 시 한 번이면 되고 자리 현황(E1)은 폴링한다 — 이 분리 덕에 지도 이미지를 반복해서 내려받지 않는다
- **부스 상세 화면(기능 1.8)은 만들지 않는다.** 이름·분류·주문 접수 여부·자리 현황을 E1 목록에 전부 담으므로 부스를 눌러 새 화면으로 들어갈 이유가 없다. 소개·메뉴 미리보기·대기 등록은 파일럿 범위 밖이다 (§8)

## E1. GET /api/v1/event/booths — 부스 목록·좌석 현황 (기능 1.7 + 1.8의 좌석 표시, v0.5 신설)

> **인증 없음.** 대표 QR로 들어온 홈 화면에서 **자리 현황 보기**에 쓰는 데이터

**Query**

| 파라미터 | 예 | 설명 |
|---|---|---|
| category | `FOOD` | 카테고리 필터 (생략 시 전체) |

**Response 200**

```json
{
  "booths": [
    {
      "boothId": 1,
      "name": "컴공 주점",
      "category": "FOOD",
      "isOpen": true,
      "mapX": 3200,
      "mapY": 5400,
      "tables": { "total": 10, "empty": 3 }
    },
    {
      "boothId": 2,
      "name": "동아리 카페",
      "category": "CAFE",
      "isOpen": false,
      "mapX": 6100,
      "mapY": 2800,
      "tables": { "total": 6, "empty": 6 }
    }
  ]
}
```

> **기능 1.8을 둘로 쪼갠 이유** — 기능명세 1.8(부스 상세)은 "소개·메뉴 미리보기·대기 현황"과 "좌석 여유/보통/만석 3단계"를 한 항목에 묶어 두었다. 앞쪽은 웨이팅 기능에 딸린 것이라 파일럿 범위 밖이고, 뒤쪽 좌석 표시만 이번에 들어온다. 그래서 **좌석 표시는 상세 화면이 아니라 E1 목록의 각 행에 얹고**, 나머지 1.8은 §8 Later에 그대로 둔다. 1.8이 두 곳에 걸쳐 보이는 것은 이 분할 때문이며 중복 배정이 아니다.

**필드 규칙**
- `tables.total`: 등록된 테이블 수 / `tables.empty`: **손님이 앉아 있지 않은 테이블 수**. **서버는 숫자만 준다**
- 화면 표시는 클라이언트가 3단계로 변환한다 — 기능 1.8의 "여유 / 보통 / 만석". 권장 임계값은 `empty/total ≥ 0.5 → 여유`, `> 0 → 보통`, `= 0 → 만석`. **임계값을 서버에 박지 않는 이유**: 행사 중 체감과 어긋나면 프론트 배포만으로 조정할 수 있어야 한다
- `mapX`·`mapY`: 약도 이미지 기준 **상대 좌표(0~10000 = 0.00%~100.00%)**. 이미지 크기가 바뀌어도 핀 위치가 유지되도록 픽셀이 아닌 비율로 저장한다. 미설정 부스는 `null` — 클라이언트는 지도에 표시하지 않고 목록에만 노출
- `isOpen`은 **주문 접수 스위치**(O17)다. 재료 소진으로 STAFF가 잠근 상태도 여기 포함되므로 화면 문구는 "영업 종료"가 아니라 **"주문 마감"** 이 정확하다. `false`인 부스도 목록에 남긴다 (마감된 것을 손님이 알아야 헛걸음하지 않음)
- 정렬: `boothId` 오름차순 (파일럿 규모에서 별도 정렬 요구 없음)

**빈자리 판정 기준 (v0.5 개정 — 중요)**

테이블의 `status` 컬럼이 아니라 **세션**으로 판정한다. 한 테이블이 "차 있다"로 세어지는 조건은 다음 둘을 **모두** 만족하는 세션이 붙어 있는 경우다.

| 조건 | 뜻 |
|---|---|
| `ended_at IS NULL` | 운영자가 퇴실(O6)을 누르지 않았다 |
| `last_activity_at > 현재시각 - 유휴임계` | 그 세션에서 최근에 무언가 했다 |

- **유휴 임계 기본값 3시간**, 설정값 `boothlock.event.seat-idle-minutes`로 조정한다. 3시간은 명세 §1.2의 세션 유휴 만료 시간과 맞춘 값이다. 축제 주점 체류 시간을 측정한 근거는 없고 **가정**이다(확정 필요 9번). 코드를 다시 빌드하지 않고 이 설정이나 환경변수 `BOOTHLOCK_EVENT_SEATIDLEMINUTES`를 바꾼 뒤 재시작하면 반영된다. 0 이하는 기동 시 거부한다
- O6 퇴실이 구현되면 퇴실 시 `ended_at`이 찍혀 **유휴 시간을 기다리지 않고 즉시** 빈자리가 된다. 이 개정 시점에는 O6가 스텁이라 세션을 종료하는 경로가 없고, 유휴 임계만 동작한다
- 한 테이블에 과거 종료 세션이 여러 건 쌓여 있어도 중복으로 세지 않는다

**`status`를 기준으로 쓰지 않는 이유** — 되돌아오는 경로가 없다. 지금 코드에는 `status`를 `EMPTY`로 돌리는 코드가 없다. 예정된 경로는 O6 퇴실인데 **O6는 현재 스텁**이다. §1.2의 세션 자동 만료는 설계상 `status`를 건드리지 않고, **만료 자체도 아직 구현되지 않았다**. 즉 지금 코드에서 테이블은 한번 `OCCUPIED`가 되면 영원히 그대로다. `status` 기준으로 집계하면 손님이 QR을 찍는 순간부터 그 자리는 영구히 만석으로 잡혀, **행사 몇 시간 뒤 전 부스가 "만석"으로 고착된다.** 세션 기준은 O6 구현 여부와 무관하게 동작하므로 E1이 O6에 발목 잡히지 않는다.

- **O6가 구현되면 더 정확해진다.** 유휴 임계를 기다리는 대신 즉시 반영되므로, O6는 여전히 우선순위가 높다. 다만 **E1의 선행 조건은 아니다**
- **좌석 수는 실시간이 아니라 폴링 시점 값이다.** 손님이 말없이 자리를 뜨면 유휴 임계가 지나야 빈자리로 바뀐다 — 화면에 "현재 기준" 정도의 문구 권장
- 판정은 양쪽으로 틀릴 수 있다. 주로는 말없이 떠난 자리가 최대 임계 시간 동안 차 있게 보이는 쪽(자리가 적게 보임)이다. 반대로 임계 시간 넘게 주문·호출·조회를 하지 않고 앉아 있는 손님의 자리는 빈자리로 보인다
- §1.2는 "미결제 주문이 남은 세션은 영업일 종료로만 만료"라고 정하지만, 이 개정 시점의 E1 판정에는 그 예외가 없다. 세션 발급(C1)·좌석 현황(O3)에 유휴 만료를 구현할 때 세 곳이 같은 정의를 쓰도록 함께 맞춘다

- `category` 필터는 대소문자를 무시한다. 비어 있거나 공백이면 전체, 모르는 값이면 빈 배열이다. 분류가 없는 부스는 `"category": null`로 나가며 필터를 주면 제외된다

**Errors**: 없음 (인증 없음, 필터가 잘못되면 빈 배열)

**성능**: 폴링 10~15초. **서버 캐시 10초 구현**(`boothlock.event.booths-cache-seconds`, 0이면 끔) — 전체 목록을 캐시하고 `category` 필터는 캐시 결과에서 건다. 캐시가 없으면 인증 없는 반복 호출이 집계 쿼리를 계속 돌려 주문 API와 DB 커넥션 풀을 다툰다(동시 50 요청에서 다른 API가 2ms→400ms로 느려지는 것 실측). 대가로 좌석 수·주문 접수 여부가 최대 10초 늦게 반영된다. 좌석 집계는 부스·테이블·세션을 LEFT JOIN 해 **GROUP BY 한 번**으로 끝낸다 — 부스마다 쿼리를 도는 구조 금지. 세션 조인 조건(`ended_at IS NULL`, `last_activity_at`)은 JOIN의 `ON`에 넣는다. `WHERE`에 넣으면 세션이 없는 테이블이 결과에서 통째로 빠져 빈자리가 0으로 나온다

## E2. GET /api/v1/event/map — 행사장 약도 (기능 1.9, v0.5 신설)

> **인증 없음.** 홈 화면의 **메인**이다. 이 약도 위에 `booth.mapX·mapY`로 부스 핀을 찍는다

**Response 200**

```json
{
  "imageUrl": "/uploads/event/map.png",
  "width": 1600,
  "height": 1200,
  "updatedAt": "2026-09-10T14:00:00+09:00"
}
```

- `width`·`height`: 원본 이미지 크기(px). 클라이언트가 화면 크기에 맞춰 축소할 때 E1의 상대 좌표를 픽셀로 환산하는 데 쓴다 — `pixelX = mapX / 10000 * 표시폭`
- **외부 지도 API를 쓰지 않는다** (2026-07-31 확정). 임시 부스는 지도 서비스에 없어 실익이 없고, 약도 이미지가 행사 안내 책자와 같은 그림이라 손님이 대조하기 쉽다
- 약도가 등록되지 않았으면 **`404 NOT_FOUND`** — 클라이언트는 지도 없이 E1의 목록만 보여준다
- 이미지는 O9 업로드와 같은 정적 서빙 규칙을 따른다 (`X-Content-Type-Options: nosniff`). **구현 완료** — `/uploads/event/**` 전용 리소스 핸들러와 nosniff 인터셉터를 별도 설정 클래스로 등록했다. 메뉴 사진 설정(`MenuUploadWebConfig`)은 메뉴 파트 소유 파일이라 건드리지 않고 같은 방식의 설정을 하나 더 두는 쪽을 택했다 — Spring은 `WebMvcConfigurer` 빈을 여러 개 합쳐 적용한다
- 업로드 디렉터리도 메뉴와 분리한다 (`boothlock.upload.event-dir`, 기본 `data/uploads/event`) — 약도와 메뉴 사진이 한 폴더에 섞이지 않게
- **인증 없이 열린 경로라 세 겹으로 막는다**: ① 폴더 설정 검증 — 마지막 폴더 이름이 `event`가 아니거나, 서버 작업 디렉터리·그 상위이거나, 파일 DB가 그 아래 있으면 기동을 거부한다(`.`으로 두면 DB 파일이 그대로 내려받아지는 것 실측) ② `png`·`jpg`·`jpeg`·`webp`만 서빙하고 숨김 파일과 폴더 밖을 가리키는 심볼릭 링크는 404 ③ `nosniff`와 `Content-Security-Policy: default-src 'none'; sandbox` 헤더
- 약도 파일이 폴더에 없으면 E2는 200으로 주소를 주지만 이미지 요청은 404가 난다 — 시딩 시 파일 존재를 확인해야 한다
- 경로 관례를 `/uploads/menu/`·`/uploads/event/`로 분리한다 — O9 명세의 예시 URL(`/uploads/xxx.jpg`)도 `/uploads/menu/xxx.jpg`로 읽을 것

**Errors**: `404` (약도 미등록)

**등록 방법**: 파일럿에서는 총관리자가 시딩으로 1건 넣는다. 운영자용 약도 업로드 API는 만들지 않는다 (행사당 1장이라 API를 둘 이익이 없음)

## C1. POST /api/v1/table-sessions — 세션 발급 (QR 스캔 직후)

**인증**: 없음 (tableToken 자체가 인증 수단)

**Request**

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| tableToken | string | ✅ | QR URL에서 추출한 테이블 토큰 |

**Response 200**

```json
{
  "sessionToken": "sess_8f2k...",
  "booth": { "id": 1, "name": "컴공 주점", "isOpen": true },
  "table": { "id": 12, "label": "A-3" },
  "restored": true
}
```

| 필드 | 설명 |
|---|---|
| booth.name / table.label | 화면 상단 **상시 표시** — 자기 자리 확인 + 가짜 QR 대응 (기능 0.1) |
| booth.isOpen | false면 "주문 접수가 마감되었습니다" 안내 (메뉴판 열람은 가능) |
| restored | true = 기존 활성 세션 복원 → 주문 내역 이어서 표시 (기능 0.2), false = 새 세션 |

**Errors**: `400`(토큰 누락) / `404 NOT_FOUND`(존재하지 않거나 재발급으로 폐기된 토큰 → "유효하지 않은 QR입니다. 부스 직원에게 문의해주세요")

**동작 규칙**
- 테이블에 활성 세션 존재 → 그 세션의 sessionToken 반환 (`restored: true`) — **테이블 단위 세션** (확정 결정 #6)
- 활성 세션 없음 → 새 세션 생성 + 테이블 상태 `OCCUPIED` 자동 전환 (기능 4.4 — "사용중 표시는 QR 스캔·주문 시 자동, 빈자리 전환은 수동만")
- 프론트: 토큰 교환 직후 `history.replaceState`로 주소창에서 tableToken 제거. **tableToken은 저장하지 않음** — 이후에는 sessionToken만 사용, 세션이 만료되면 QR 재스캔 (§7-8)

## C3. POST /api/v1/orders — 주문 생성 (기능 2.3)

**Request 헤더**: `Idempotency-Key: {UUID}` **필수** — 클라이언트가 주문 시도마다 `crypto.randomUUID()`로 생성, 네트워크 재시도 시 같은 키 재사용. 누락 시 `400`

**Request Body**

| 필드 | 타입 | 필수 | 검증 |
|---|---|---|---|
| items | array | ✅ | 1~20종 |
| items[].menuId | int | ✅ | 해당 부스의 노출 중 메뉴. 미존재·타 부스 menuId는 `400` (미존재로 취급) |
| items[].qty | int | ✅ | 1 ≤ qty ≤ 30 |

```json

```

**Response 201**

```json

  "orderId": 101,
  "orderNo": "A3-17",
  "status": "RECEIVED",
  "paymentStatus": "UNPAID",
  "totalAmount": 21000,
  "items": [
    { "menuId": 3, "menuName": "김치전", "unitPrice": 8000, "qty": 2, "subtotal": 16000 },
    { "menuId": 5, "menuName": "제로콜라", "unitPrice": 5000, "qty": 1, "subtotal": 5000 }
```

**서버 검증 (순서대로)**
1. 세션 유효성 → `410`
2. 부스 `isOpen` → false면 `409 ORDER_CLOSED` (기능 8.3)
3. **멱등성**: `unique(idempotencyKey)` **단일 컬럼** — 같은 키의 재요청은 새 주문을 만들지 않고 **기존 주문을 200으로 그대로 반환** (더블탭·네트워크 재시도 안전. ~~복합 unique(sessionId, idempotencyKey)~~는 sessionId가 null인 수기 주문에서 무력화됨이 실측 확인되어 v0.4.3에서 단일로 정정. ~~"동일 items 3초 거부"~~는 일행 두 명이 같은 메뉴를 동시 주문하면 오탐이라 폐기 — 검증 반영)
4. rate limit: 세션당 미결제(RECEIVED+UNPAID) 주문 최대 **8건** → 초과 시 `429 ORDER_RATE_LIMITED`. (세션이 테이블 단위이므로 3건은 4인 일행의 정상 주문도 막음 → 8건으로 확정. 진짜 어뷰징 방어의 본진은 §7-1 "입금 확인 후 조리" — 검증 반영)
5. 각 메뉴 존재·노출·품절 **재검증** (기능 2.2) → 미존재는 `400`, 품절/숨김 포함 시 `409 SOLD_OUT` + details에 해당 메뉴 전체 목록 → **주문 전체 실패** (부분 주문 없음)
6. **금액은 서버 DB 가격으로 재계산** — 요청에 금액 필드 자체가 없음 (위변조 원천 차단)

**규칙**
- `orderNo` 채번은 §2 규칙 (부스 영업일 통산, FOR UPDATE 채번 — `A3-17`)
- `payment.bankAccount`는 **운영자가 부스 설정에 등록한 값만** 서버가 내려줌 (기능 3.2 — 위변조 방지)

## O3. GET /api/v1/admin/tables — 좌석 현황 (기능 4.4 보조)

```json
{
  "tables": [
    {
      "id": 12, "label": "A-3", "status": "OCCUPIED",
      "posX": 120, "posY": 240,
      "session": { "startedAt": "...", "lastActivityAt": "..." },
      "unpaidOrderCount": 1
    },
    { "id": 13, "label": "A-4", "status": "EMPTY", "posX": 260, "posY": 240, "session": null, "unpaidOrderCount": 0 }
  ]
}
```

> ⚠️ **명세 ↔ 구현 불일치 (v0.5에서 발견) — v0.5.1 해소안: 합집합**
>
> 현재 구현(PR #32 머지분)은 `session`·`unpaidOrderCount` 대신 **`needsCleanup`(boolean)** 하나를 반환한다. 둘 중 하나를 고르는 대신 **셋을 다 내려주는 안**을 제안한다.
>
> - 이미 머지된 `needsCleanup`을 **그대로 둔다** → 쓰고 있는 화면이 깨지지 않는다. 필드를 빼는 변경만 하위 호환을 깬다
> - `session`·`unpaidOrderCount`를 **더한다** → 운영자 POS 화면(9/7 결정 3)은 테이블을 눌러 주문 정보를 봐야 하므로 미결제 건수가 실제로 필요하다. `needsCleanup`만으로는 "퇴실해도 되는 자리인지"를 판단할 수 없다
> - `needsCleanup`은 `status = OCCUPIED && session == null`로 서버가 계산한 값이다. 클라이언트가 `session`으로 직접 판정하지 않고 서버 판정을 그대로 쓰게 두는 편이 낫다 — 판정 규칙이 바뀌어도 화면을 안 고친다
>
> **회의 확정 필요**: 이 합집합으로 갈지, 한쪽으로 줄일지. 정해지면 O22 응답도 함께 따른다

- 퇴실(O6)·QR 다운로드(O4)·재발급(O5) 화면의 테이블 목록 소스 (O2 응답 보관으로도 대체 가능하나 이 API 사용 권장)
- `unpaidOrderCount`: **`RECEIVED && UNPAID` 주문 수** (C3 rate limit과 동일 조건 — 취소된 미결제는 미포함, 검증 반영). 퇴실 전 미결제 확인용
- `lastActivityAt`: 마지막 주문·호출·**조회 폴링** 시각 (§1.2 활동 정의와 동일). 이용 시간 모니터링(4.5)은 Later지만 필드만 미리 포함
- **`status: OCCUPIED` + `session: null`** = 세션이 자동 만료됐지만 퇴실 처리 안 된 테이블 (§1.2 자동 만료는 status를 안 건드림). 화면에 '정리 필요' 뱃지 + 퇴실 버튼 활성 (검증 반영). **이 개정 시점의 구현에서는 세션을 종료하는 코드도 유휴 만료도 없어 이 상태가 발생하지 않는다** — O6와 유휴 판정 공유가 들어가야 동작한다
- **`posX`·`posY` (v0.5 신설)**: 운영자 배치도에서 테이블 상자를 놓을 위치. **좌표계 단위는 px이며 배치도 캔버스 좌상단이 원점**이다. 좌표를 정하지 않은 테이블은 `null` — 클라이언트는 배치도 밖 "미배치" 영역에 모아 두고 끌어다 놓게 한다. 저장은 O22
- 배치도가 없어도 목록 화면으로는 그대로 쓸 수 있다 — 좌표는 표시 방식일 뿐 좌석 현황의 의미를 바꾸지 않는다

> ⚠️ **E1과 O3가 같은 테이블을 다르게 말한다 (v0.5.1 검증에서 발견 — 테이블 파트 수정 필요)**
>
> 손님 화면(E1)은 5시간 유휴 테이블을 **빈자리**로 셉니다. 같은 테이블을 운영자 화면(O3)은 **`OCCUPIED` + `needsCleanup: false`** 로 보여줍니다. 현재 `needsCleanup` 판정이 `status = OCCUPIED && 활성 세션 없음`인데, 유휴 세션은 `ended_at`이 NULL이라 "활성"으로 잡히기 때문입니다.
>
> **실제로 생기는 일**: 손님은 홈 화면에서 "빈자리 있음"을 보고 그 부스로 갑니다. 운영자 POS에는 그 자리가 그냥 사용중으로 떠 있고 정리하라는 표시도 없습니다. 운영자가 치우지 않아 손님이 앉을 수 없습니다. **화면 두 개가 다른 말을 하는 것이 문제의 본질**이고, 어느 쪽이 맞느냐보다 둘이 같은 기준을 쓰는 것이 중요합니다.
>
> **수정 방향**: O3의 활성 세션 판정에 E1과 같은 유휴 임계를 건다. `ended_at IS NULL` 뿐 아니라 `last_activity_at > 현재 - 임계`까지 만족해야 활성으로 본다. 그러면 유휴 테이블이 `needsCleanup: true`로 잡혀 운영자 화면에 "정리 필요" 뱃지가 뜬다. 임계값은 E1과 **같은 설정값**(`boothlock.event.seat-idle-minutes`)을 읽어야 두 화면이 갈라지지 않는다.
>
> 담당은 테이블 파트다. E1 쪽을 O3에 맞추는 반대 방향은 택하지 않았다 — 그러면 좌석 현황이 다시 영구 만석으로 돌아간다

```json
  ]
```

- 컬럼: `주문번호, 테이블, 주문시각, 메뉴명, 수량, 단가, 금액, 주문상태, 결제상태, 결제수단, 승인자, 승인시각, 취소자, 취소시각, 취소사유, 환불처리자, 환불처리시각`
- **수식 주입 방지**: 자유 입력 필드(메뉴명·취소사유)가 `= + - @`로 시작하면 `'` 를 앞에 붙여 출력
- 취소·환불 주문 포함 (정산 검증용 전체 원장). `date`는 영업일 기준, 행사 전체는 영업일별 다운로드 후 병합 (파일럿 확정). 파일럿은 CSV만 — PDF 없음

## O21. POST /api/v1/admin/orders/{orderId}/refund-done — 환불 완료 처리 (기능 5.5 보조, **ADMIN 전용**)

## O22. PATCH /api/v1/admin/tables/{tableId}/position — 테이블 배치 좌표 저장 (기능 4.6 보조, v0.5 신설)

> 운영자 메인 화면의 배치도에서 테이블 상자를 끌어다 놓은 결과를 저장한다

**Request**

| 필드 | 타입 | 필수 | 검증 |
|---|---|---|---|
| posX | int | ✅ | 0 이상. 배치도 캔버스 좌상단 원점 기준 px |
| posY | int | ✅ | 0 이상 |

```json
{ "posX": 120, "posY": 240 }
```

**Response 200**: 갱신된 테이블 1건. **O3의 테이블 항목과 정확히 같은 형태**를 쓴다 (O3의 형태가 확정되면 이 응답도 함께 따른다 — 위 O3 각주 참조)

```json
{
  "id": 12, "label": "A-3", "status": "OCCUPIED",
  "posX": 120, "posY": 240,
  "session": { "startedAt": "...", "lastActivityAt": "..." },
  "unpaidOrderCount": 1,
  "needsCleanup": false
}
```

> 위 예시는 O3 각주의 **합집합 안**을 따른 것이다. 회의에서 O3 형태를 줄이기로 하면 이 응답도 같이 줄인다 — 두 곳의 형태가 갈라지면 클라이언트가 테이블 항목을 두 벌로 파싱해야 한다

**Errors**: `400`(값 누락·음수) / `404`(타 부스 테이블·미존재 — 존재 은닉) / `401`

**규칙**
- 테이블 하나씩 저장한다. 배치도에서 여러 개를 옮겼다면 클라이언트가 옮긴 것만 순차 호출한다 — 파일럿 규모(테이블 수십 개)에서 일괄 저장 API를 둘 이익이 없다
- 좌표는 **표시 전용**이다. 주문·세션·QR 어디에도 영향을 주지 않으므로 잘못 저장돼도 운영에 지장이 없다
- 겹침을 서버가 막지 않는다 — 배치도에서 상자가 겹치는지는 화면에서 판단할 문제다

# 5. 총관리자 API (`/api/v1/super/*`, `SUPER_ADMIN` 전용 — 기능 8.2)

> "총관리자(부스락 운영팀)가 부스 등록·계정 발급·정지·비밀번호 재발급 처리". 부스 운영자(`ADMIN` 포함)가 호출 시 `403`. SUPER_ADMIN의 `/admin/*` 접근도 `403` (§1.2 — 양방향 차단).
> 8.2는 CSV상 Must이나 파일럿은 **DB 시딩으로 대체** (확정 결정 #11) — 경로만 확정.
> **v0.5 변경**: 파일럿이 복수 부스가 되면서 시딩 범위가 늘었다. 행사 전에 시딩으로 넣어야 하는 것은 ① 부스들(name·bankAccount·category·mapX·mapY) ② 부스별 ADMIN 계정 ③ **행사 약도 1건(EventMap)** 이다. 부스가 하나였을 때는 손으로 한 줄 넣으면 됐지만 이제는 시딩 스크립트가 실질적으로 필요하다
> (경로를 `/admin`과 분리한 이유: 권한 필터를 경로 프리픽스로 단순하게 걸기 위함 — `/api/v1/admin/booths` vs `/api/v1/admin/booth` 한 글자 차이 사고 방지 겸)

| # | Method | Path | 기능 | Request 핵심 |
|---|---|---|---|---|
| A1 | POST | `/api/v1/super/booths` | 부스 등록 | `{ name, bankAccount, category, mapX, mapY }` (v0.5: 지도 필드 추가) |
| A2 | POST | `/api/v1/super/staff` | 운영자 계정 발급 | `{ loginId, password, boothId, role(ADMIN|STAFF) }` — SUPER_ADMIN 발급 불가(시딩 전용) |
| A3 | PATCH | `/api/v1/super/staff/{staffId}` | 계정 정지·비번 재발급·잠금 해제 | `{ active: false }` / `{ password: "새비번" }` / `{ unlock: true }` |

- A2의 `boothId`는 존재하는 부스인지 검증
- A3로 **정지 시**: `active` 매 요청 확인으로 기존 JWT 즉시 차단. **비번 재발급 시**: `passwordChangedAt` 갱신 → `pwdAt` 클레임 비교로 기존 JWT 즉시 무효 (§1.2 — 검증 반영으로 메커니즘 분리 명시)
- 이메일 기반 비밀번호 재설정 없음 — 총관리자 재발급 방식 (기능 8.2)

**시딩 산출물 (v0.5 신설 — 복수 부스 전환으로 실질 필수가 됨)**

행사 전에 다음이 DB에 들어가 있어야 E1·E2가 빈 화면이 아니다.

| 대상 | 내용 | 비고 |
|---|---|---|
| 부스 N개 | `name`, `bank_account`, `category`, `map_x`, `map_y` | 좌표는 약도를 보고 측정 |
| 부스별 ADMIN 계정 | `login_id`, `password_hash`, `role=ADMIN`, `booth_id` | 부스마다 최소 1개 |
| 테이블 | 부스별로 O2 일괄 등록 사용 | 시딩 대신 운영자가 화면에서 해도 됨 |
| 행사 약도 1건 | `event_map` (image_url·width·height) | 이미지 파일은 `/uploads/event/`에 배치 |

- **구현 주의**: `spring.jpa.hibernate.ddl-auto=update` 환경에서 `data.sql`을 쓰려면 `spring.jpa.defer-datasource-initialization=true`가 필요하다. 스키마 생성보다 데이터 삽입이 먼저 일어나 실패하는 것을 막는다
- 형식(`data.sql` vs 시더 클래스)·담당자는 확정 필요 항목 참조

# 6. 데이터 모델 (ERD 요약)

```
Booth 1─N Table 1─N TableSession(활성 최대 1개) 1─N Order 1─N OrderItem N─1 Menu
Booth 1─N Menu / 1─N StaffAccount / 1─N Feedback(운영자 평가) / 1─N BoothAccountChangeLog
EventMap (행사 약도 1건, 부스와 직접 관계 없음 — 부스 핀은 Booth.mapX/mapY가 가진다)
TableSession 1─N Call
```

| 엔티티 | 핵심 필드 | 비고 |
|---|---|---|
| Booth | name, bankAccount, isOpen, operatingHours, **category, mapX, mapY** | category·mapX·mapY는 v0.5 신설 — 홈 화면(E1·E2)용. mapX·mapY는 0~10000 상대 좌표 |
| Table | boothId, label(정규화 후 최대 6자·대문자), **tableToken**(unique·CSPRNG 128bit+), status(EMPTY/OCCUPIED), **posX, posY** | posX·posY는 v0.5 신설 — 운영자 배치도 표시용(px). null 허용 |
| TableSession | tableId, **sessionToken**(unique), startedAt, endedAt(null=활성), lastActivityAt | 테이블당 활성 세션 최대 1개. MySQL은 부분 unique 인덱스가 없으므로 `unique(tableId, endedAtKey)`(활성=0, **종료 시 자기 id 기록** — epoch초는 같은 초 2건 종료 시 충돌해 v0.4.3에서 정정) 사용. 상세는 DB 스키마 v1.3 (검증 반영 — 초심자가 막히는 지점) |
| Menu | boothId, name, price, imageUrl, description, **soldOut**, visible | **stock 없음 (확정)** |
| Order | boothId, sessionId(수기 미지정 시 null), **businessDate, orderSeq**, orderNo, **idempotencyKey**, status(RECEIVED/DONE/CANCELED), paymentStatus(UNPAID/PAID/REFUND_NEEDED/REFUNDED), paymentMethod, totalAmount, cancelReason, **approvedBy, approvedAt, canceledBy, canceledAt, refundedBy, refundedAt**, isManual, createdAt | **unique(boothId, businessDate, orderSeq)** + **unique(idempotencyKey) 단일** (v0.4.3 정정 — 복합은 수기 주문의 null sessionId에서 무력화). orderSeq 채번은 §2 (FOR UPDATE — auto-increment 금지) |
| OrderItem | orderId, menuId, **menuName(스냅샷), unitPrice(스냅샷)**, qty | 가격 변경에도 과거 주문 불변 |
| StaffAccount | boothId(**SUPER_ADMIN은 null**), loginId(unique), passwordHash, **passwordChangedAt**, role(**SUPER_ADMIN**/ADMIN/STAFF), active, failedLoginCount, lockedUntil | |
| BoothAccountChangeLog | boothId, changedBy, changedAt, oldValue, newValue | 계좌 변경 감사 |
| Call | sessionId, reason(HELP/WATER/ETC), acked, createdAt | |
| Feedback | boothId, staffId, rating, easySetup, easyOrders, wouldReuse, comment, createdAt | 운영자의 서비스 평가 (7.4) |
| **EventMap** | imageUrl, width, height, updatedAt | v0.5 신설 — 행사 약도 1장(E2). 파일럿은 단일 행, 시딩으로 등록 |

- 시스템 에러 알림(기능 9.2)은 API 아님 — 서버 전역 에러 핸들러(@ControllerAdvice)에서 디스코드/슬랙 웹훅 호출. 계좌 변경 알림(O17)도 같은 웹훅 사용
- 삭제 정책: 메뉴·테이블·주문 전부 **소프트 삭제 또는 삭제 없음** — 행사 종료 후 CSV 정산 뽑고 일괄 폐기가 기본 라이프사이클
